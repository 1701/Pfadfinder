# ARCHITECTURE.md – Pfadfinder

Status: v1.0 · gilt für das MVP · Erweiterungspunkte in Abschnitt 9

## 1. Grundsatz

Client-only PWA. Kein Backend, keine Datenbank außerhalb des Geräts, kein Netzwerkzugriff nach dem Laden. Alles, was fachlich ist (Mastery, Scheduling, Probetest-Auswertung), lebt in reinen TypeScript-Funktionen ohne React-Abhängigkeit und ist unit-getestet. React ist nur Darstellung.

## 2. Stack (festgelegt)

Versionen: aktuelle stabile Majors, Stand siehe `package.json`.

| Zweck | Wahl | Begründung |
|---|---|---|
| Build | Vite + TypeScript strict | schnell, PWA-Plugin ausgereift |
| UI | React, React Router (Library-Modus, kein Framework-Modus) | Claude-Code-Stärke, großes Ökosystem |
| Styling | Tailwind CSS (CSS-first, Tokens per `@theme`) | schnell iterierbar, Design-Tokens zentral |
| State | Zustand | klein, kein Boilerplate; Persistenz über eigenen Adapter |
| Persistenz | Dexie (IndexedDB) | strukturiert, migrierbar, Export/Import als JSON |
| Validierung | Zod | Schema aus `CONTENT_SCHEMA.md` 1:1 als Zod-Types; Build-Zeit-Validierung |
| PWA/Offline | vite-plugin-pwa (Workbox) | Precache aller Content-Dateien |
| Drag & Drop | @dnd-kit/core | Touch-tauglich, zugänglich |
| Vorlesen | Web Speech API (SpeechSynthesis, `de-DE`) | kein externer Dienst; Fallback: Button ausgeblendet |
| Druck | Print-Stylesheet + `window.print()` | PDF via Browser; keine PDF-Lib im MVP |
| Tests | Vitest + Testing Library; Playwright (3 Smoke-Flows) | Domain 100 % unit, UI pro Format ein Test |
| Lint | ESLint (typescript-eslint, react-hooks, jsx-a11y), Prettier | |
| CI | GitHub Actions: lint → content-validate → test → build | Content-Fehler brechen den Build |
| Hosting | Cloudflare Workers mit Static Assets, gebaut von Workers Builds bei Push (`wrangler.jsonc`, `docs/DEPLOY.md`) | kostenlos, keine Betriebslast, Vorschau-URL je Branch |

Keine weiteren Laufzeit-Dependencies ohne Eintrag in `CLAUDE.md` Abschnitt "Dependencies".

## 4. Domänenmodell (persistiert in IndexedDB)

```ts
Learner        { id; name?: string; createdAt; settings: { readAloud: boolean; bundesland: "BW" } }
Attempt        { id; learnerId; itemId; fach; bereich; niveau; format; correct: boolean | 0.5; answer: unknown;
                 durationMs; mode: "check" | "practice" | "review" | "probetest"; at: ISO }
MasteryState   { learnerId; fach; bereich; niveau: 1|2|3; window: (0 | 0.5 | 1)[] /* letzte 8, Kurzantwort "teils" = 0.5 */; mastered: boolean; updatedAt }
ReviewEntry    { learnerId; itemId; dueAt: ISO; stage: 1 | 2 | "done" }         // Fehlerkiste: +1 Tag, +3 Tage
Session        { id; learnerId; mode; startedAt; endedAt?; attemptIds: string[]; goalReached: boolean }
ProbetestRun   { id; learnerId; probetestId; startedAt; status: "running"|"submitted"|"aborted"; endedAt?; endReason?: "submit"|"time"|"leave"|"expired";
                 currentIndex; answers: Record<itemId, Draft>; itemMs; attemptIndex; ratings: Record<itemId, 1|0.5|0>; attemptIds;
                 result?: { byBereich: Record<Bereich, {solved, total, pending}>; total: {solved, total, pending} } }   // kein Prozent (2026-10-15)
Collectibles   { learnerId; unlocked: string[] }                                 // Entdeckungen je gemeisterter Etappe
PostponedOffer { fach; at: ISO }                                                  // "Später" beim Einstieg-Angebot (gilt seit Aufgabe 12 für alle Fächer des Tages); geräteweit, nicht im Export (Dexie v2)
```

Export-Format: `{ version: "2", exportedAt, learner, attempts, mastery, reviews, sessions, probetestRuns, collectibles }` als JSON-Datei. Import validiert mit Zod und migriert nach Versionsnummer: v1 → v2 (2026-10-15) gibt jedem Probetest-Lauf einen Status (mit `submittedAt` „submitted“, sonst „aborted“/„expired“), leere Entwürfe und ein Ergebnis ohne Prozent mit abgerundeten gelösten Items. Das Export-Format ist das spätere Sync-Format (Roadmap v2).

## 5. Kernabläufe

**Üben.** `scheduler.pickNext(bereich, masteryState, recentItemIds, pool)` → Item auf aktuellem Niveau, nicht in den letzten 20 gesehen, Formatwechsel bevorzugt. Nach Antwort: `evaluation.check(item, answer)` → `mastery.update(state, correct)` → bei falsch `scheduler.enqueueReview(itemId, now)`; gebündelt in `practice.recordPracticeAnswer`. Session-Ziel 10 Items, danach Abschluss-Screen. Gezogen werden nur Items mit registriertem Renderer; ein Bereich ist erst ab `MIN_ITEMS_FOR_PRACTICE` (10) solcher Items übbar. **Tagesgrenze:** Eine offene Session (ohne `endedAt`) wird nur am Kalendertag ihrer letzten Aktivität fortgesetzt (Zeit des neuesten Attempts, ohne Attempts `startedAt`; lokale Zeit des Geräts), und nur, wenn alle ihre Attempts im gewählten Bereich liegen. Wer um 23:55 beginnt und um 00:03 noch antwortet, setzt um 00:10 dieselbe Session fort. Offene Sessions, deren letzte Aktivität an einem früheren Tag lag, schließt `practice.planSessionStart` beim Start eines Bereichs (`endedAt` = jetzt, `goalReached` = false), danach beginnt eine neue. Eine Session wird erst mit ihrer ersten Antwort gespeichert. **Fortsetzen oder neu anfangen** (seit 2026-10-14): Gibt es eine solche Session von heute mit Antworten, zeigt der Store den Status `choosing` (`ui/screens/UebenWahl`). „Fortsetzen“ macht dort weiter; „Neu anfangen“ (`data/practice.restartPractice`) schließt sie mit `practice.closeSession` (`endedAt` = jetzt, `goalReached` = false, ohne Abschluss-Screen) und beginnt eine neue Runde mit `SESSION_GOAL` Items über `pickNext`. Attempts, Mastery, Fehlerkiste und Entdeckungen bleiben, das Tagesziel springt also nicht zurück. **Entdeckungen:** Ein Aufstieg von Niveau n schreibt `"<bereich>:<n>"`, „gemeistert“ schreibt `"<bereich>:3"` in `Collectibles.unlocked`; Einträge werden nie gelöscht, so bleibt eine erreichte Etappe auf der Karte gefüllt, auch wenn das Niveau sinkt. **Lesetexte** (seit 2026-10-16): Hat das letzte Item der Runde einen `textRef`, nimmt `pickNext` zuerst die Items dieses Textes, die in der Runde noch nicht dran waren (`sessionItemIds`, aus `session.attemptIds`), das Niveau am nächsten zum Mastery-Niveau zuerst, bei Gleichstand das leichtere. Erst wenn keins übrig ist, gelten wieder Fehlerkiste, Niveau und die letzten 20. **Abweichung vom bisherigen Verhalten (gewollt):** Solange ein Text läuft, darf `pickNext` Items aus den letzten 20 wiederholen, und fällige Wiederholungen warten bis zum Textende (Test `pick-next-text`). `practice.readingStep(item, source, shownTextIds)` entscheidet: erstes Item eines Textes in der Runde → Status `reading` (Lese-Screen) vor dem Item; weitere Items und Fehlerkiste-Wiederholungen → Text neben dem Item, ohne Lese-Screen. `shownTextIds` hält der Store nur im Speicher, nach Neuladen kommt der Lese-Screen wieder. Die Zeit des Items beginnt nach „Weiter“ auf dem Lese-Screen. **UI** (seit 2026-10-16, Teil C): `ui/screens/LeseScreen` (Zeile „Lies den Text.“ mit Vorlesen für Anweisung und Titel, darunter `TextKasten` mit Titel, gelb „Weiter“). Beim Item steht `ItemScreen.text` = `TextKasten` ohne Titel (`.item-with-text`): quer eine Spalte links, `--spacing-reading-column` 34 % unter 768 px Höhe und `--spacing-reading-column-tall` 42 % ab 768 px; hoch ein Block mit der Höhe Bildschirm − `--spacing-reading-reserve-<format>` (gemessen in `text-layout.spec`: je Format die Reserve, bei der der engste Zustand 18 px Luft behält; innerhalb eines Items stabil, mindestens `--spacing-reading-box-min`). Nur der Kasten scrollt; der Verlauf unten zeigt weiteren Text, oben (`data-more-above`) schon gelesenen, beide statisch. `ui/text-scroll` hält die Scrollposition je Text über die Items einer Runde, nach dem Lese-Screen beginnt sie oben. Vorlesen: Der Item-Knopf liest `itemSpeech` (nie den Text), der Kasten-Knopf `textSpeech` (Titel und Absätze, unverändert), nur bei `ReadingText.readAloud`; im Probetest entscheidet `probetest.probetestTextReadAloud(fach, item, text)` (Deutsch: immer aus, seit Aufgabe 13 verdrahtet). Vorschau `/dev/text/:id?item=…&zustand=…` und eine echte Runde `/dev/text/:id?runde` (In-Memory-Repos, Fixture `tests/fixtures/lesen`, nur Dev). **match neben dem Text** (seit Aufgabe 15): Die Grenzen in CONTENT_SCHEMA §4.4 (1.0.17) stammen aus `tests/e2e/sweep-match.spec.ts` mit der Fixture `tests/fixtures/sweep-match` (deren Items zeigen auch `/dev/text` und `/dev/probetest` mit deutsch-90). Das Playwright-Projekt `sweep` gibt es nur mit `PFADFINDER_SWEEP=1`, nie in CI und nie in `npm run e2e`; drei Tests (Summe, `-g Rückmeldung`, `-g Prompt`) schreiben nach `tests/e2e/output/sweep-match*.json`. Die Luft folgt Zeilen, nicht Zeichen: entscheidend sind Zahl der Paare und Zeilen des Prompts. **Luft je Item** (seit 2026-10-22): `tests/e2e/sweep-luft-items.spec.ts` (ebenfalls Projekt `sweep`, Item-IDs in `PFADFINDER_SWEEP_ITEMS`) misst Items aus `content/` in vier Viewports, Üben über `/dev/item`, Durchsehen über `/dev/probetest` (seit 2026-10-27) am echten Platz jedes Probetests, der das Item enthält: durchsehen, bei Kurzantwort durchsehen-vergleichen, und fehlt (Schlüssel `…@<probetest>`). Der Platz zählt: An Platz 24 heißt der Knopf „Zur Auswertung“ statt „Weiter“, im Zustand fehlt wird die Meldung dadurch schmaler und das Band höher (m-dz-3-003: 44 px an Platz 24 von mathe-03, 70 px an einem früheren Platz). Nur ein Item ohne Probetest nimmt den Platz des ersten Items gleichen Formats in `<fach>-01` ein. `failing` folgt `airWanted` (≥ 18 px, Ausnahmen nur `AIR_EXCEPTIONS`). Ausgabe `tests/e2e/output/sweep-luft-items.json` mit Luft und `promptLines` je Zustand. **Tagesziel:** `todayProgress(attempts, day, sessions)` zählt `practice`- und `review`-Attempts des lokalen Kalendertags von `day`, höchstens 10. **Satz vor dem ersten Fundstück** (seit Aufgabe 17): Solange es auf keinem Tag ein Fundstück gab (`hasFundstueck(attempts)`, dieselbe Regel `isFundstueck` wie im Tagesziel; Check- und Probetest-Attempts zählen nicht), liefert `loadMapProgress` `foundAny: false` aus den ohnehin gelesenen Attempts, ohne eigenes Feld in Dexie. Die Karte zeigt dann im Tagesziel „Jede Aufgabe, die du übst, bringt dir ein Fundstück.“ in Tinte: quer an Stelle der leeren Wegstriche über „Heute …“, hoch in einer Zeile an Stelle von Strichen und „Heute …“. So bleibt der Kopf gleich hoch und die Karte gleich groß (gemessen: eine zweite Zeile machte die Gebietsnamen in Safari hoch 17,8 px, mit „Neu laden“ 16,5 px). Vorgelesen über den Knopf am Titel nach „Heute: 0 von 10 Fundstücken.“. Während das Einstiegsangebot steht, gibt es kein Tagesziel und keinen Satz; ohne lesbaren Speicher auch nicht, weil er nie verschwinden könnte. Die Karte liest beim Öffnen neu, also ist er nach dem ersten Fundstück, nach Neuladen und nach dem Einlesen einer Sicherung mit Fundstücken weg. Seit Aufgabe 10 zählt eine Antwort für den Tag, an dem ihre Runde begann (`Session.startedAt`), nicht für ihre eigene Uhrzeit. Der Abschluss-Screen nimmt den Starttag seiner Runde; die Karte `progress.practiceDay`: den Starttag einer offenen Runde von einem früheren Tag, die nach Mitternacht noch weiterläuft (letzte Antwort heute, sie würde also fortgesetzt), sonst jetzt. Nach dem Abschluss einer solchen Runde zeigt die Karte den neuen Tag.

**Startseite und Content-Laden.** `scripts/validate-content.ts` erzeugt bei gültigem Content `content/manifest.json`: je Bereich die Zahl der aktiven Items (ohne `retired`) je Format und Niveau sowie die Text-IDs, dazu die Probetest-IDs je Fach (seit 1.0.9). Die Datei ist erzeugt, nicht handgeschrieben, und kein Teil des Item-Vertrags (CONTENT_SCHEMA). Ein Test vergleicht sie mit dem Content, in CI ist ein veraltetes Manifest ein Fehler, und der pre-commit-Hook verlangt das Stagen. Die Startseite ist die Karte (`src/ui/map`, Liste als Fallback unter `/?liste`). Sie liest das Manifest und danach aus dem lazy Chunk `map-progress` (Dexie) Mastery, Entdeckungen und die Attempts für das Tagesziel; `mapRegionState(manifest, mastery, unlocked, formats)` ergibt je Gebiet (10 seit 2026-10-25: 5 Mathe, 5 Deutsch; Lage in `ui/map/geometry.ts`, hoch T1, quer W1b aus SU Phase A) unerforscht / neu / unterwegs / gemeistert mit den erreichten Etappen. Ein Bereich ohne Items (wie `sprache-untersuchen` bis zum ersten Batch) ist wie jeder mit < 10 übbaren Items `unerforscht`. Die Items eines Bereichs lädt erst die Üben-Route, aus je einem Content-Chunk pro Bereich; mit ihnen `loadTexts(fach, bereich)` die Lesetexte (ein lazy Chunk je Textdatei, im Precache, geprüft von `check-bundle`), zugeordnet über `ReadingText.kind` (sachtext → lesen-sachtext, literarisch → lesen-literarisch), nicht über den Dateinamen. `createContentLoader(modules)` nimmt andere Quellen nur für Tests und Dev-Seiten (Fixture `tests/fixtures/lesen`). Store, Dexie, Zod und die Renderer liegen im lazy Chunk `practice-route`. `scripts/check-bundle.ts` hält das JS der Startseite unter 300 kB und frei von Zod und Dexie. React Router läuft deklarativ (`BrowserRouter`/`Routes`), der Daten-Router wird nicht gebraucht.

**Einstiegscheck.** Pro Fach einmal, nur übbare Bereiche (`practiceableBereiche`), je 2–3 Items, höchstens `CHECK_ITEM_COUNT[fach]` (je 15: Mathe seit Aufgabe 15, Deutsch seit 2026-10-25 mit `sprache-untersuchen`, vorher 12). `scheduler.buildCheck(fach, pool, { bereiche, seed })` liefert einen Plan (Bereiche in Rundenreihenfolge, `total`, gemischte Kandidaten; Seed = Session-ID). `nextCheckItem(plan, answers)` wählt das Item der aktuellen Leiterstufe (`checkLadderNiveau`: richtig hoch, falsch bleibt) und nach Runde 2 die Bereiche mit drittem Item (zuerst gemischt beantwortete). In einem Lesen-Bereich kommen alle 2–3 Items aus einem Text: Der Seed wählt einen Text mit mindestens 2 prüfbaren Items, nur dessen Items sind Kandidaten (seit 2026-10-16). Lesen-Bereiche stehen als zusammenhängender Block nach den Runden der übrigen Bereiche (seit Aufgabe 10, vorher davor: erst die kurzen Aufgaben, der lange Text am Ende), mit allen ihren Plätzen (2–3, ohne Runde-3-Auswahl; gekürzt auf `CHECK_ITEM_COUNT` wird nur Runde 3; `check.test` prüft das für jede Teilmenge der Deutsch-Bereiche und verlangt `CHECK_ITEM_COUNT.deutsch` ≥ 2 × Runden-Bereiche + 3 × Lesen-Bereiche); vor dem ersten Item kommt der Lese-Screen (Status `reading` im Check-Store, „Pause“ kehrt dorthin zurück). Das Startniveau ist `checkStartNiveau` = höchstes Niveau mit richtiger Antwort, mindestens 1. `check.completeCheck` erzeugt daraus je geprüftem Bereich einen `MasteryState` (Fenster leer), Entdeckungen für die Etappen darunter und eine Session mit mode "check". `data/check.finishCheck` speichert Attempts, Session, Mastery und Entdeckungen in **einer** Transaktion, erst nach der letzten Antwort und nur, wenn das Fach noch keinen `MasteryState` hat; vorher steht alles nur im Store (`data/check-store`). Ein Abbruch hinterlässt deshalb nichts. Check-Attempts ändern weder Mastery noch Fehlerkiste noch Tagesziel. Die Karte bietet den Check über `progress.mapOffer` an: solange `progress.isCheckOffered` gilt (kein `MasteryState` im Fach, mindestens `CHECK_MIN_BEREICHE` = 2 übbare Bereiche), heute noch kein Fundstück gezählt ist und der Speicher lesbar ist. Höchstens ein Angebot pro Tag (seit Aufgabe 12): "Später" speichert `data/map-progress.postponeOffer` als `PostponedOffer` in Dexie, und `progress.offerSpentToday` gilt bis zum Ende des lokalen Kalendertags (Grenze wie beim Fortsetzen) als verbraucht, sobald ein "Später" (egal welches Fach) oder eine beendete Session mit mode "check" von heute vorliegt, auch nach Neuladen; solange eine Runde von diesem Tag nach Mitternacht weiterläuft (`practiceDay`), gilt der Tag weiter (seit Aufgabe 10). UI: Route `/einstieg/:fach` im lazy Chunk `check-route` (eigener Store, `CheckStoreContext`), Screens in `ui/screens/Einstieg*`. Der Item-Screen ist derselbe wie beim Üben, mit `submitLabel` "Weiter" und `pause.onPause` statt Link. Das Ergebnis zeigt `Karte` mit `fach` (zugeschnitten über `islandViewBox`) und `interactive={false}`. Status `unavailable` unterscheidet `started` (Hinweis "Deine Reise hat schon begonnen.", auch wenn `finishCheck` nichts schreibt) und `empty`. Vorschau unter `/dev/einstieg?zustand=…` (nur Dev).

## 6. Format-Renderer

`src/ui/formats/registry.ts` mappt `Item.format` → React-Komponente mit einheitlichem Vertrag:

```ts
type FormatProps<F extends Format> = {
  item: ItemOf<F>;
  attemptIndex: number;           // Seed fürs Mischen: presentationSeed(item.id, attemptIndex)
  answer: DraftOf<F> | null;      // = AnswerOf<F>, bei short-answer nur { text } (die Wertung kommt aus dem Band)
  onChange(answer: DraftOf<F> | null): void;  // null = noch keine gültige Eingabe ("3,"), Prüfen bleibt aus
  disabled: boolean;              // nach Abgabe und beim Vergleichen
  revealed?: { correct: Correctness; solution: SolutionOf<F> };  // Feedback-Darstellung
  showSolution?: boolean;         // short-answer: Musterlösung zeigen (Vergleichen und danach)
};
type FormatEntry<F> = { component; selfRated?: true; submitLabel?: string; bandNote?(item): { label; text } };
```
Seit 2026-10-11: `attemptIndex` und `onChange(… | null)` ergänzt, weil das Mischen formatspezifisch ist und unfertige Eingaben gemeldet werden müssen. Seit 2026-10-14 (Aufgabe 7) sind alle neun Formate registriert (`SUPPORTED_FORMATS`), seit 2026-10-25 zehn mit `segment-text` (CONTENT_SCHEMA 1.0.25); `MIN_ITEMS_FOR_PRACTICE` zählt damit alle aktiven Items. Ein Registry-Eintrag kann mehr als die Komponente: `selfRated` (short-answer: der Knopf heißt `submitLabel` „Vergleichen“, der ItemScreen zeigt danach Musterlösung und Selbsteinschätzung „Getroffen / Teils / Noch nicht“ im Band, erst diese Wahl ruft `onSubmit(answer)` mit `rating`; das Band zeigt danach keine Überschrift), `bandNote` (find-error: „So schreibt man es: …“ im Band, bei richtig und noch nicht). match und order bringen dnd-kit mit und liegen in eigenen Chunks: `preloadFormats()` lädt sie, sobald die Üben- oder Einstieg-Route ihren Store anlegt; das Promise trägt Reacts Statusfelder, `use()` liest ein geladenes Modul also synchron. `scripts/check-bundle.ts` prüft, dass dnd-kit (Marker `DndDescribedBy`) in keiner Datei steckt, die Startseite oder eine Route statisch laden. Ziehen ist nie der einzige Weg: match geht mit Tippen (Zeile oder Feld, dann Karte, oder umgekehrt), order mit den Knöpfen ↑/↓. Das leere Zielfeld bei match sieht aus wie die leere Lücke bei cloze-select (seit Aufgabe 14: `emptyTileClass` und „…“ in `ui/formats/choice`). - Updates (seit Aufgabe 11): Die App registriert den Service Worker selbst (`app/pwa-update.ts`, `registerType: 'prompt'`) und fragt beim Start und bei jeder Rückkehr in den Vordergrund nach einer neuen Version.
